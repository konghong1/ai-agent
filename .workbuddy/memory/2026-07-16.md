## 任务 31 排查：卡在「创作中」的僵尸 running
- 现象：用户反馈任务 31 一直「创作中」。核查：task 31 `status=running, done=0/18, failed=0, records=0`，`created_at==updated_at==2026-07-15 10:01:20`（进度字段自创建从未变）；同用户任务 30(18/18)、29~26 均 completed，**唯独 31 卡死 24h+**。
- 根因：`gallery_worker` 用 api 进程内**内存队列**（`queue.Queue()`）。`docker restart ai-agent-api`（历史迁移 restart loop + 今日多次重启）清空队列+worker 线程死亡 → 原 running 任务**永久僵尸**：没人接管、进度永远 0、也不标 failed（hang 不抛异常/新进程不知有此任务）。属「假 running」，非真失败。
- **如何判断失败（回答用户）**：① `status='failed'`+有 `error`=真失败（worker 跑完抛异常/预检查拦截）；② `status='running'` 但 `done/failed/records` 长时间不变+`created_at` 陈旧=**卡死/僵尸**（任务 31 即此）；③ `status='completed'/'partial'`=成功。
- 修复：① `gallery_worker._recover_orphans` 启动恢复孤儿 running（带 PROCESS_START-120s 阈值防活跃任务重复生成）；② `delete_task` 卡死 running（created>30min）放行删除；③ 前端 `isStuck` 提示+卡死可删。
- 验证：后端 py_compile 通过；前端 `npm run build` 通过；`docker restart api/web`；容器内 `delete_task` 三场景——卡死 running 放行(True)✓、活跃 running 拒绝✓、pending 拒绝✓；任务 31 仍在(running done=0)未被误删，用户 Ctrl+F5 后前端删除按钮可用，点确认即清理。
- 注意：任务 36（running, created 03:06）暴露「无阈值 recovery 会重入队活跃任务→重复生成」隐患，已用 PROCESS_START-120s 阈值修复（36 当时已消失，未造成重复数据）。

## 修复：电商套图「重做」点完直接显示失败、无进度（🔥ORM 对象误传后台线程）
- 现象：用户点单图「重做」→ 图片不显示「生成中」进度，直接显示「生成失败」。
- 根因（两层，均在 `app/gallery_service.py` 的 `regenerate_record`）：该函数把请求线程里的 ORM 对象（用户传 `user`、记录 `rec`）直接交给了后台线程 `_do` 去用。请求一返回，`get_db` 会话关闭 → `user`/`rec` 变成 **detached/expired**：

  2. 第二层（修掉第一层后暴露）：`_do` 里 `rec.title` 触发懒加载 → `InvalidRequestError: This session is provisioning a new connection; concurrent operations are not permitted`。
  两处异常都被 `regenerate_record._do` 的 `except` 捕获 → 记录被误置 `status='failed'`、`result_url=None`。毫秒级崩，前端轮询 2.5s 后只看到 `failed`，故“没进度、直接失败”。
- 修复（与代码既有模式 line 1606 `user_id = user.id # 关闭会话前提取` 一致）：在**主线程、会话还活着时**把后台线程要用的所有 ORM 字段取成普通变量——`uid = user.id`、`rec_title = rec.title`、`rec_type_id = rec.type_id`，`_do` 内一律用这些本地变量，绝不再碰 `user`/`rec`。前端 `doRedo` 提交成功后立即 `setTasks` 把该记录乐观标为 `processing`（带 `data-record-id` 的单元格属性，便于 E2E 锁定）。

## 修复：电商套图「很多图片一直生成中」永久卡死（🔥双层根因）
