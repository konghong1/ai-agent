## Docker 镜像瘦身 + 历史胖镜像清理
- 背景：用户点 Docker Desktop 删 `ai-agent-worker:latest` 报 `Image ... is in use. Delete the container that's using it`。根因：容器 `ai-agent-api`/`ai-agent-worker` 引用着 9.41GB 的 `latest` 胖镜像，Docker 禁止删被引用的镜像。
- 根因（已修复于 7-16 23:04）：老 Dockerfile 用 `COPY . .` 且当时 `.dockerignore` 缺失/不全，把宿主机 1.5GB `.venv`+前端产物塞进镜像 → 9.41GB。现 `docker/Dockerfile.api` 为 Plan B 瘦身版（python:3.12-slim + 多阶段，去掉 torch/sentence-transformers），根目录 `.dockerignore` 已正确排除 `.venv/ node_modules/ web/ dist/ .git/` 等，未来 `docker compose build` 不会复胖。
- 执行（均安全：两容器已 exited 且可写层 nil，源码靠 `volumes: ../:/app` bind mount 不存容器内）：
  1. `docker rm ai-agent-api ai-agent-worker`
  2. `docker rmi 6d01a354b7a8 399c44da49d7`（两个 9.41GB 胖镜像已删）
  3. `docker tag ai-agent-api:planb2 ai-agent-api:latest` + 同 tag 到 `ai-agent-worker:latest`（瘦身镜像 6e4cfd1700b7 / 1.45GB，api 与 worker 共用同一 slim 镜像，compose 靠 CMD 区分）
  4. `docker image prune -f` + `docker builder prune -f`（回收 ~18.5GB 构建缓存）
- 验证：`docker compose up -d` 全栈正常（mysql/minio healthy，api/worker Up），`docker inspect` 确认两容器 image=sha256:6e4cfd1700b7（slim）。API 日志无致命错误（仅 egress proxy 不可达的 benign 警告，已走直连兜底）。
- 磁盘对比：Images 40GB→9.6GB（~30GB 释放），Build Cache 18.5GB→43MB（~18.5GB 释放），合计释放约 48GB。
- 注意：未动 volumes（含 mysql_data/minio_data 真实数据，禁止 prune）；未删 `compose-*`/`trend-radar` 等无关旧容器（非 9G+ 且未要求）。
- 可选后续（未执行，需用户确认）：本地 `.venv` 1.3GB 若仅用于非 Docker 开发可保留；旧的 `compose-*`(878MB×4) 与 `trend-radar` 停止容器/镜像如不再用可单独清理。

## 聊天会话上下文传递分析 + 超长处理方案（架构设计）
- 分析结论：同一 Thread 内上下文靠 `app/agent.py:ask_agent()` 每次 `select(Message).where(thread_id=...)` **全量加载所有历史**原样塞进 prompt（`agent.py:326-348`），由 `/chat`(`api.py:669`) 与 `/chat-stream`(`api.py:813`) 调用。
- **对会话历史完全无任何超长处理**：无 token 预算、无滑动窗口、无截断、无摘要；唯一 `max_tokens` 逻辑是 RAG 片段的 `ContextBuilder.max_context_tokens`(`agent.py:303`/`services.py:775`) 与出图提示词预算，都不限制聊天历史；无模型级 `context_window` 配置。长会话会爆窗或上游静默截断。
- 额外坑：现有分词启发式 `len(content)//3.5`(`services.py:789`) 英文调参，对中文低估约 5 倍。
- 设计出方案（参考 Claude Code 的 auto-compaction）：引入独立 `ContextManager` 模块，预算驱动（model_context_window − reserve_for_response）、始终保留 system(pinned)+最近 K 轮原样、超预算时对窗口外旧轮次做 **LLM 增量摘要** 持久化到 `Thread.summary`/`last_compacted_msg_id`；原始 Message 永不删（可逆）；中文-aware 分词；RAG 额度纳入同预算；压缩失败降级为滑动窗口丢弃；UI 透明标注 `used_compaction`。
- 数据模型：`Thread` 加 `summary`(TEXT 可空)/`last_compacted_msg_id`(INT 可空)/`compacted_at`；迁移遵守 MySQL TEXT 禁默认值的硬约束。
- 落地：feature flag 默认关闭可灰度回滚；Phase 0 tokenizer+context_window 字段 → Phase1 ContextManager → Phase2 灰度+UI → Phase3 可选向量记忆召回(C)。
- 交付物：`designs/chat-context-compaction-design.md`（含 ADR-021 + 流程示意图）。

## 最终统一方案：融合 gbrain（ADR-023）
- 用户要求结合 GitHub `garrytan/gbrain`（Agent 长期记忆/检索大脑层）与前面两版，出最终方案。已读仓库：gbrain=markdown 知识库 + Postgres/PGLite + 混合检索 + auto-link 图谱 + cron 富集 + Retrieval Reflex（零 LLM 确定性指针层：扫实体→注入紧凑指针 name→slug→synopsis，detect+point 不转储、fail-open、capped）+ schema packs + gap analysis。
- 交付物：`designs/final-unified-context-memory-architecture.md`（ADR-023 + 融合管线图）。
- 核心收敛：设一等模块 `ContextService`，统一模型窗口预算下装配 `[pinned] + [记忆召回：Retrieval Reflex 指针(零LLM,gbrain) + Chroma 语义回忆] + [会话摘要 ADR-021] + [最近K轮] + [RAG] + [当前轮]`。
- 对 gbrain 取舍：**采纳** brain-first lookup、Retrieval Reflex 指针层、cron 富集、schema packs(→L0-L3)、gap analysis(可选)；**改编** signal capture 为「显式优先+隐式候选队列默认关需确认」(多用户防污染)、auto-link 缩为「实体归一」；**暂不采纳** MCP 30+工具/PGLite 双引擎(沿用本项目 Chroma+SQLAlchemy 零新依赖)。
- 落地对接点：`ask_agent` 全量加载替换为 `ContextService.build()`；复用 `vector_store.VectorStoreBackend`/`get_embeddings`；新增 `UserMemory`/`PendingMemory` 表 + `Thread.summary` 列；`MemoryEnricher` 守护线程接 `server.py::startup`（同 gallery worker 不联网范式）；中文-aware 分词替换 `services.py:789 len//3.5`。分阶段 P0-P7 各有独立开关，出问题即关对应层。

2. **SQLite vs MySQL 测试陷阱**：容器外跑 seed 脚本连到 SQLite 而非 API 的 MySQL → 种子数据 API 不可见 → 假 404/假失败。种子必须在 api 容器内执行或走 API 自身端点。
3. **toast 进入动画首帧 off-screen 是正常的**：antd message enter animation 从 translateY(-100%) 开始，~300ms 后稳定到可见位置。测试 poll 应等待动画完成或取末段样本而非首帧。
4. **改动必须浏览器预览验证**：改完 CSS/组件须实际打开页面确认视觉符合预期（本次截图证实 toast 可见且美观）。
