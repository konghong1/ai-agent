**实现方案（推荐 Option A）**：给 `ask_agent` 加 `stream: bool = False` 参数；`stream=False` 维持原 tuple 返回（771/814 不动），`stream=True` 时变为生成器（yield status/delta/done、在 done 前 commit 助手消息以保证历史持久化）。`ask_agent_stream_gen` 的 complex 分支改为 `for ev in ask_agent(stream=True,...): yield ev`。这样逻辑单点、无重复、契约安全。

**正确性风险（须管理）**：生成器持有独立 session，须在 `done` 前把 assistant 消息 commit 落库（保持现有"生成器 own session、结束 commit"契约），否则用户中途断连会丢历史。P1(搜索超时+缓存)/P2(并行工具/MCP schema 缓存/避免 nudge) 在此基础上叠加。

## 完成 P0+P1+P2 实现 + 验证（聊天重型路径优化）

## 聊天每轮加载性能「设计级」优化讨论（2026-07-20 晚，用户主动提）

用户诉求：当前「工具+上下文」每轮全量重载太慢，希望**识别是否需要知识库再走 ContextService 检索**，并参考 `shareAI-lab/learn-claude-code`(imperial-harness 教学 repo)做"极致性能、每轮最优"的设计。
已读准代码链路（`agent.py` build 段 / `context_service.py` / `mcp_tools.py`）：
- `complex_path = enable_context_service OR enable_mcp_tools OR enable_skill_tools OR enable_hooks` —— **静态恒真**，不区分单轮是否需要。
- `ContextService.build()` 每轮必做：`_workspace_memory`(文件) + `_core_memory`(DB) + `_user_profile_memory`(DB) + `_retrieval_reflex`(正则抽实体+扫 500 行 UserMemory) + **`_semantic_recall`(`MemoryStore().query()` = embedding + Chroma 向量检索，即"知识库")** + `_get_state`(DB) + 超额 `summarizer`(LLM)。
- 之后 `get_mcp_tool_catalog`(拼巨大文本块) + `build_mcp_langchain_tools`(**每轮为每个 enabled server 的每个工具重建 StructuredTool 对象**) → `bind_tools` → LLM。

提出的设计（已画 3 张图给用户）：
- **Pillar A 每轮意图路由**：<50ms Fast Intent Router(规则+可选轻量分类)把单轮分 T0 直答(<2s)/T1 工具(跳过 KB)/T2 全量三档，替代静态 complex_path。
- **Pillar B 知识库门控**：① 前置门控——Router 判"本轮需不需要知识库"，不需要则完全跳过 `semantic_recall`(省 embedding+Chroma)；② 按需检索工具——把 `semantic_recall` 改为 `retrieve_knowledge(query)` 工具，模型判定需要才调用(s07 on-demand 模式)。KB 检索从"每轮必做"降到"仅 ~30% 轮、且只针对本条 query"。
- **Pillar C 工具池缓存+剪枝(s02/s19)**：`build_mcp_langchain_tools` 改为**缓存**(key=(user_id, 配置 hash))，MCP 增删改**事件失效**(非 IDLE_TTL 时间过期)；`bind_tools` 前 top-k 相关性剪枝只绑最相关工具，catalog 瘦身为"名称+一句话"。

实施建议分阶段（已向用户给出 a/b/c 选项，待用户拍板）：
- 阶段1(低风险立竿见影)：工具池缓存+事件失效+catalog 瘦身+KB 前置门控(规则版)。
- 阶段2(激进)：Fast Intent Router 三档分流 + `retrieve_knowledge` 按需工具 + top-k 工具剪枝。
