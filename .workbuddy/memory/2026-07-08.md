## 删除会话后端崩溃（My‍SQL 1038 Out of sort memory）— 真正的根因

用户点击确认删除后会话仍存在，后端抛 `sqlalchemy.exc.OperationalError: (1038, 'Out of sort memory...')`，SQL 为 `SELECT messages ... WHERE ? = messages.thread_id ORDER BY messages.created_at`。

**根因**：`delete_thread` 原实现用 `db.delete(thread)` + 模型关系 `Thread.messages` 设了 `cascade="all, delete-orphan"` 且 `order_by="Message.created_at"`。SA 执行级联时会**先把 messages 集合懒加载出来再逐条删**，这条 `ORDER BY created_at` 的 SELECT 在 MySQL 上触发 filesort；当 `sort_buffer_size` 偏小或该会话消息很多时，直接 1038 报错 → 整个 DELETE 事务回滚 → 会话"删不掉"。

**修复（app/api.py: delete_thread）**：不再走 ORM 级联，改为按 `thread_id` 直接 bulk delete：
1. `db.query(Message).filter(thread_id==tid).delete(synchronize_session=False)`
2. 顺手清掉无 FK 级联、但引用 thread_id 的 `KBFeedback` / `RetrievalLog`
3. `db.query(Thread).filter(id==tid, user_id==uid).delete(...)`
4. `db.commit()`
`Query.delete()` 直接发 `DELETE ... WHERE thread_id=?`，**无 ORDER BY / 无 filesort**，从根上消除 1038。

**附带加固（app/models.py Message）**：加复合索引 `ix_messages_thread_created (thread_id, created_at)`，让"按会话加载消息"的 `WHERE thread_id=? ORDER BY created_at` 走索引、不 filesort（对大消息表的读路径也有益）。
> 注意：现有 MySQL 库不会因 `create_all` 自动加该索引，需对线上库手动执行 `CREATE INDEX ix_messages_thread_created ON messages (thread_id, created_at);`（新库 / SQLite 无影响）。

**验证**：TestClient 建含 50 条消息的会话 → DELETE 返回 204、消息与 thread 行均清零；线上 curl 连续删两条均 204、列表剩余 0。前端改动（Popconfirm + destroyPopupOnHide）上一轮已完成，本次后端修复与前端互补，彻底解决"删除异常"。

涉及文件：`app/api.py`、`app/models.py`。

## 三个问题收尾（本轮实测验证通过）

用户进一步报了 3 个现象，已修复并端到端验证：

### 1. 查消息仍报 1038 Out of sort memory（旧库缺索引）
- **根因**：复合索引 `ix_messages_thread_created` 虽加进了 `app/models.py`，但线上库是索引加进模型**之前**建的；`Base.metadata.create_all()` 只对"不存在的表"生效，**不会给已存在的旧表补索引** → `WHERE thread_id=? ORDER BY created_at` 一直 filesort → 小 `sort_buffer_size` 下 1038。
- **修复（app/db/__init__.py）**：新增幂等 `ensure_indexes()`，用 `inspect` 检查索引是否存在再 `CREATE INDEX`，并在 `init_db.main()` 的 `create_tables()` 之后调用 → 以后无论新旧库每次启动自愈。实时库已手动 `CREATE INDEX` 验证 `EXPLAIN` 走索引、`Extra: NULL`（无 filesort）。
- **加固（docker-compose.yml mysql command）**：加 `--sort-buffer-size=4M`（原 256K）。已 `docker compose up -d mysql` 重建容器生效（`SHOW VARIABLES` 确认 4194304）。

### 2. 上传参考图 422 Unprocessable Entity
- **根因（web/src/pages/ChatInterface/index.tsx）**：上传 `fetch` 用了 `headers: authHeaders()`，该函数注入 `Content-Type: application/json`；但 body 是 `FormData`，浏览器不会自动加 multipart boundary → Starlette 找不到 `file` 字段 → 422。日志里 "选择参考图 生成图片失败" 由此引发。
- **修复**：该上传请求去掉 `Content-Type` 覆盖，让浏览器自己加 `multipart/form-data; boundary=...`。重建 dist（nginx 服务 `web/dist`），curl 验证：正确 multipart → 200，带 `Content-Type:application/json` → 422（复现根因）。

### 3. 刷新/切模块后聊天内容没了
- **根因**：`activeThreadId` 是纯组件内 state，刷新或切模块重挂后回到默认（首个/空）会话；叠加问题 1 的 500 会让 `fetchMessages` 把消息清空。
- **修复**：`activeThreadId` 持久化到 localStorage（`ACTIVE_THREAD_KEY="active-chat-thread"`），`switchThread` 写入、`fetchThreads`（mount 时调用）读取并恢复到已存在的会话。重建 dist 已部署（首页引用 `index-Bv4K2j1q.js`）。

## 参考图生成 `do_request_failed` 完整根因与最终修复（本轮）

用户二次报 `do_request_failed`，并追问"本地上传图为啥没进 minio"。坐实两个根因：

### A. 根因：超大参考图 → 上游挂死/失败（已被本轮根治）
- **复现（决定性）**：用真实手机原图尺寸测试，内联后请求体大小与上游行为：
  - 6MB 参考图（2432×3248）→ 上游**直接挂起**，45s 客户端 `ReadTimeout`。
  - 2.7MB 参考图（1600px）→ **HTTP 200，60s 出图**。
  - 阈值在 ~2000px：超过即上游处理不过来 → 表现为 `do_request_failed`（网关返回错误）或 `ReadTimeout`（网关上游处理挂死）。
- **修复（唯一切入点 `app/storage/__init__.py` 的 `inline_reference_image`）**：取回原图后先用 Pillow 把长边压到 **≤1280px** 并转 JPEG，再 base64 内联。该入口同时被 chat LLM 路径（`agent.py`）与图片/视频生成路径（`media.py` 的 `_normalize_reference_images`）复用，一处修复全覆盖。
  - 新增 `_downscale_image_bytes(raw, max_side=1280, quality=85)`：非 JPEG 小图原样返回（保质量）；需缩放或 PNG 则缩图+转 JPEG；**Pillow 缺失/解码失败则原样返回**（fail-safe，绝不阻断内联）。
  - 实测：4.7MB 手机原图上传 → 内联压到 **1MB**（4695KB→1009KB），落在安全区。
- **Pillow 持久化**：`requirements.txt` 加 `Pillow>=10.0.0`；容器内 `pip install Pillow`（12.3.0）。重建镜像时会自动带。

### B. 根因：用户看错桶，"图没进 minio"是误解
- 上传走 `POST /api/chat/upload`（`app/api.py:363`），存到**独立桶 `chat-uploads`**（与生成的 `ai-agent-minio` 严格分离，见 `MEMORY.md` 存储桶用途）。
- 实测 `chat-uploads` 桶现有 16 个对象，含用户 05:11:39 上传的 1.2MB PNG（05:11:45 才报生成失败）——证明**上传与落盘完全正常**，图一直在 minio，只是不在用户盯着的 `ai-agent-minio` 桶。
- 结论：无需改上传逻辑，只需告知用户去 `chat-uploads` 桶看。

### C. 附带加固 `media_retry.py`
- 把 `model_not_found` / `no available channel`（上游常返回 **503**）列为**永久错误、不重试**：原实现因 `status_code>=500 → return True` 短路，503 被误判瞬时、白重试 3 次（~16s）。修复后**先解析错误体、先排除永久错误，再判 5xx**。实测坏模型 1.3s、1 次即返回干净错误。
- `clean_provider_error` 实测生效：线上 api 现已返回**清洗后的纯文本错误**（如 `upstream error: do request failed (request id: ...)`），不再吐原始 JSON——用户上一轮看到的原始 JSON 是旧代码未重载所致，本轮已 `restart` 生效并验证。

## 聊天消息在切换会话/tab 时丢失 —— 根因与修复（本轮·关键）

用户报：生成图片/视频时切换 tab 页（或切换会话），当轮聊天（用户消息+生成结果）丢失。

### 根因：客户端断开时 SSE 生成器的 DB 会话生命周期竞态
- 旧 `chat_stream` 的 `event_generator` 在文本分支用 `temp_db = SessionLocal()` 建会话，`finally: temp_db.close()` 在生成器被取消时关闭它；图片/视频分支则复用 `Depends(get_db)` 的请求会话（请求结束/客户端断开时由 FastAPI 关闭）。
- 当用户**切换 tab/会话**（前端 `chatAbortRef.abort()` 或组件卸载触发 `AbortController.abort()`）→ 客户端断开 → SSE 生成器被取消 → 会话被**立即关闭**，而此时 `asyncio.to_thread` 里的 `_handle_image_generation` / `ask_agent` 还在 `db.commit()` → 提交被打断/会话已关闭 → **该轮 user+assistant 消息写入失败、丢失**。重载 `fetchMessages` 自然查不到 → 表现为"聊天丢失"。
- 注意：后端 `ask_agent`（agent.py:265/390-395）与 `_handle_image_generation`（api.py:466-516）/`_handle_video_generation`（api.py:547-570）**本来就会落库**；问题出在"落库那一刻的会话被客户端断开关掉了"，不是没写。

### 修复（解耦会话与会命周期）
- 新增 `app/api.py` 两个助手，**在 worker 线程内自建并关闭自己的 DB 会话**：
  - `_run_text_chat(...)`：线程内 `SessionLocal()` → `ask_agent(db=...)` → `finally: db.close()`。
  - `_run_media_chat(media_kind, provider_id, model_name, payload, user_id)`：线程内 `SessionLocal()` → 重新 `db.get(Provider/User)` 与 `_resolve_provider_model`（避免跨会话传 ORM 对象）→ `_handle_image/_video_generation(db=...)` → `finally: db.close()`。两个分支的 `provider/user` 改为按 id 在线程内重新加载，杜绝把请求会话的 ORM 对象跨线程传。
- `chat_stream` 文本/图片/视频三处改为 `await asyncio.to_thread(_run_text_chat/_run_media_chat, ...)`，并**删除**原 `temp_db` 与 `finally: temp_db.close()`。客户端断开取消生成器时，worker 线程的会话不受影响，仍会完整 commit+close → 消息必落库。
- 前端无需改动：`handleSend` 仅当 `activeThreadIdRef.current===threadId` 才把 assistant 消息加进 state；断开时不加，但后端已落库；重载 `fetchMessages` 即恢复。视频 on 重载由 `useEffect([messages])` 自动重连 processing 的 SSE watch。

### 验证（决定性）
- **确定性集成测试（容器内）**：stub `MediaService.generate_image` 为瞬时假数据；建 thread → `asyncio.create_task(runner())` 跑到 0.3s 即 `task.cancel()`（模拟 tab 切换/客户端断开）→ 等 2s 让 worker 线程跑完自己的 commit。查 DB：`[('user',..),('assistant', blocks)]` 两条**均落库** → **PASS**。这正面证明了"生成器被取消，worker 会话仍独立提交"。
- 真实 HTTP 回归：`POST /api/chat-stream` 返回 200（修复过程中一度因 Edit 误删 `@router.post("/chat-stream")` 装饰符导致 422，已修正并 `restart`）。

### 顺带修复：uvicorn `--reload` 导致容器 OOM（`Cannot allocate memory`）
- 用户贴的 `watchfilesreload.py ... WatchfilesRustInternalError: Cannot allocate memory (os error 12)` 是容器内 `--reload` 文件监视器把 bind-mount 的整棵源码树 inotify 监视撑爆内存。
- `docker/docker-compose.yml` 的 api `command` 去掉 `--reload`（改为 `exec uvicorn app.server:app --host 0.0.0.0 --port 8010`）；`docker compose up -d api worker` 重建容器 + 烘焙 Pillow（12.3.0 已 `import` 成功）。容器不再有文件监视器 → 无该 OOM。
- 注：`restart` 不会重读 compose command，必须 `up -d` 重建容器（本轮已踩过）。

涉及文件：`app/api.py`（`_run_text_chat`/`_run_media_chat` + `chat_stream` 三处调用）、`docker/docker-compose.yml`（去 `--reload`）。

## 轮询/内存疑问解答（给用户）
- **内存不足**：就是上面 `--reload` 的 watchfiles OOM，已去掉。运行时 api 已无文件监视器，内存稳定。
- **轮询损耗性能？** 视频状态用的是 **SSE（EventSource）服务端推送，不是客户端轮询**：仅对 `status==="processing"` 的视频建一条长连接；`completed`/`failed` 立即关闭；断线指数退避重连（2/4/8/16/32s，最多 5 次），卸载/完成时清理 timer。无任何 `setInterval` 忙轮询；`fetchMessages` 只在切换会话/手动刷新时各跑一次。开销可忽略。
