## 聊天并发能力诊断（2026-07-21 上午）
- 用户问：「我这个 app 支持多少人同时在线聊天？？」
- **当前架构**：单进程 uvicorn（无 `--workers`） + LLM 同步阻塞；
- **同时在线（不发消息）**：可支持数百人（空闲连接不占 CPU）；
- **同时发消息**：**只能 1 个人**（LLM 调用阻塞整个进程）；
- **问题**：一个复杂请求卡住 → 其他请求全部排队等待。
- **三个设计缺陷**：①单进程 uvicorn；②没有超时隔离（LLM 不响应等满 120s）；③没有熔断/降级。
- **建议立刻改**：①分层超时（connect 10s, read 60s）；②多进程 uvicorn（`--workers 4`）。

## 并发能力修复（2026-07-21 中午）
- 用户质疑：「用自己的 API key 为什么还会互相影响？」「只支持一个人同时在聊天是怎么想的？」
- **根因**：单进程 uvicorn + 同步阻塞调用 → 一个请求占用整个进程 → 其他请求排队。
- **修复**：
  1. `docker/docker-compose.yml`：`--workers 4` → 可同时处理 4 个并发请求；
  2. `app/agent.py`：分层超时 `httpx.Timeout(connect=10.0, read=60.0, write=30.0, pool=10.0)` → 请求不会无限卡住。
- **验证**：并发测试通过（两个请求并行处理，总耗时 ≈ max(请求1, 请求2)）。
- **效果**：用户 A 的请求卡住，不会影响用户 B/C/D。

## 聊天超时失败提示优化（2026-07-21 下午）
- 用户需求：「聊天都卡死了，等待回复的动画孩子，要告诉用户是否失败」「回复可能需要执行多步，每步超时时间短些，但每次收到回复可重置」
- **实现**（双保险超时 + 活动重置）：
  1. `app/api.py` `/chat-stream`：
     - **chunk_timeout**: 60秒无新chunk视为卡死（精准判定）
     - **total_timeout**: 180秒总时间兜底（防无限跑）
     - **重置机制**：收到delta时重置`_last_chunk_time`，容忍"慢但有响应"的多步任务
     - **心跳提示**：每10秒返回`{"status": "正在处理中...(X秒)"}`让用户知道还在跑
  2. `app/agent.py` `_stream_once`：chunk级超时监控（60s无新chunk抛TimeoutError）
  3. 错误提示友好化：超时→「网络请求超时」；连接失败→「无法连接AI服务」；认证失败→「API认证失败」
- **设计优势**（对比之前的90秒绝对超时）：
  - ✅ 容忍"慢但有响应"：多步任务每步60秒，总时长可达3分钟
  - ✅ 精准判断卡死：60秒无chunk才判定失败，而非90秒绝对时间
  - ✅ 防恶意占用：180秒总超时兜底，无法无限跑
- **验证**：
  - 功能完整性：简单聊天HTTP 200正常返回
  - 超时提示：60秒无chunk返回`{"error": "LLM响应超时，请稍后重试。"}`
  - 心跳提示：等待期间每10秒返回`{"status": "正在处理中...(X秒)"}`
  - 并发能力：3个并发请求并行处理（多进程生效）
- **用户可见变化**：
  - 聊天不再无限卡死：60秒无响应→明确失败提示
  - 等待期间有进度反馈：用户知道"还在处理"而非"卡死了"
  - 多步任务更友好：每步有60秒缓冲，总时长可达3分钟

- **验证**：
  - Token统计：测试通过（"Hello, world!" = 4 tokens，消息列表正确计数）
  - 前端构建：成功（19.76s，无错误）
  - 功能完整性：圆环显示、点击弹窗、分项明细、超限提示
- **数据流**：
  ```
  用户发送消息 → ask_agent_stream_gen
    ↓ 计算 token usage → yield ("token_usage", {...})  ← 前端更新圆环
    ↓ 判断是否超限 → 超限则压缩 → yield ("status", "压缩中...") → 重新计算
    ↓ 调用 LLM.stream()
    ↓ 每个 chunk: yield ("delta", text)  ← 前端逐字显示
    ↓ 检测 finish_reason == 'length' → yield ("warning", "回答被截断")
    ↓ 结束 → yield ("done", {...})
  ```

  - 点击圆环查看分项明细（系统提示词、工具、消息、MCP、技能）
  - 使用率≥80%时自动压缩历史对话

## 聊天架构重构设计（2026-07-21 下午）
- 用户需求：「基于 `learn-claude-code` 重构聊天架构，去掉无条件 RAG、删除硬编码 Intent Router、工具池首次加载后缓存、Hook 系统管理扩展点」
- **设计理念**（Claude Code）：
  - Agency comes from model, not from code orchestration
  - 模型决定何时调用工具，代码只执行模型请求
  - Hook 围绕循环，不改循环
- **核心变化**：
  1. **删除无条件 RAG**：知识库检索改为 `retrieve_knowledge` 工具，模型按需调用
  2. **删除 Intent Router**：T0/T1/T2 分流逻辑删除，统一为单一 agent_loop
  3. **Tool Pool 缓存**：MCP 连接 + Skills manifest 首次加载后缓存，配置变更时失效
  4. **Hook 系统**（基于 s04_hooks）：
     - UserPromptSubmit：用户提交消息时（注入上下文）
     - PreToolUse：工具执行前（权限检查、日志）
     - PostToolUse：工具执行后（输出处理）
     - Stop：响应生成后（会话统计）
- **架构图**：见 `designs/plan-chat-architecture-refactor.md`
- **预期收益**：
  - 简单聊天延迟：3-5s → 1-2s（-50%）
  - 知识库聊天延迟：8-15s → 5-8s（-40%）
  - 工具调用延迟：每次 500ms → 首次 500ms，后续 0ms（-90%）
  - 代码复杂度：1200+ 行 → 300 行核心循环（-75%）
- **下一步**：实施 Phase 1（Hook 系统）→ Phase 2（agent_loop 重构）→ Phase 3（Tool Pool）→ Phase 4（API 集成）→ Phase 5（测试验证）
