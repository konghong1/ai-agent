## 仓库根目录混入保留名文件 `nul` 导致 `git add .` 失败（2026-07-10 傍晚）
- **现象**：`git add .` 报 `error: short read while indexing nul` / `error: nul: failed to insert into database` / `fatal: adding files failed`。
- **根因**：仓库根有个 3713 字节文件名叫 `nul`，内容是 `docker info` 的完整输出。来源是某次在 **Git Bash** 里跑了 `docker info > nul` —— Bash 里空设备是 `/dev/null`，`nul` 会被当成普通文件名落成文件（cmd 里 `> nul` 才是空设备）。而 `nul` 是 Windows/DOS 预留设备名（同 CON/PRN/AUX），git/Windows API 读写它时直接失败。
- **删除套路（重要，记牢）**：`nul` 是保留名，普通 `del nul` / `rm nul` / PowerShell `Remove-Item` / `\\?\` 前缀都不可靠（PowerShell `Test-Path \\?\...` 还会误报"不存在"）。**唯一稳的姿势**：写个 `.bat` 文件内容为 `del /f /q \\?\D:\workspace\ai-agent\nul`，再用 Git Bash 直接 `./xxx.bat` 执行（Git Bash 跑 .bat 会自动 `cmd /c` 调起，cmd 原生 `del \\?\` 能绕过保留名检查真正删掉）。删完 `ls nul` 报 No such file、`git status` 不再出现 `?? nul` 即成功。注意：在 Git Bash 里直接 `cmd //c "del ..."` 会因 `//c` 被 Git Bash 当路径吞掉而不执行，必须走 .bat。
- 顺带提醒用户：`git add .` 不受 `.dockerignore` 影响，会把 `.venv/`、`node_modules/`、`web/`、`uploads/` 等全量暂存；如需避免，应补一个 `.gitignore`。

## 事故：schemas.py 漏 import 导致 api 崩溃、用户误以为数据丢失（23:3x）
- 现象：用户反馈"重新运行后账户信息丢失"。实际 **数据没丢**（MySQL `users`=3、`gallery_projects`=2 完好）。
- 根因：上一轮改 `app/schemas.py` 给 `GalleryTemplateRead` 加 `@model_validator(mode='before')`，但忘了在 `from pydantic import ...` 里导入 `model_validator`，导致 uvicorn 加载 `schemas.py` 时 `NameError: name 'model_validator' is not defined`，api 容器 `restart: unless-stopped` 无限重启循环 → 前端所有请求失败 → 表现为"账户/数据丢失"。
- 附带两处隐患一并修：(1) `@model_validator(mode='before')` 在 `from_attributes=True` 模式下收的是 ORM 对象不是 dict，根本不生效 → 改为 `mode='after'` 从 `self.payload` 提取 `cover_url`；(2) `GalleryTemplateCreate` 被重复定义两次（644 行带 cover_url、708 行无），后者覆盖前者 → 删掉 708 行的旧定义。
- 修复后：`docker compose restart api`，日志末行 `Application startup complete.`；`curl /docs`→200、`/api/gallery/types`→401（正常受保护路由），确认存活。
- **关键教训（重要）**：`python -m py_compile` 只查语法，查不出运行期 `NameError`/`ImportError` 这类导入期错误。改后端 Python 后**不能只靠 py_compile**，必须在容器起来后做实际 HTTP 验证（如 `curl /docs` 看 200、`curl` 受保护路由看 401 而非 500/连接拒绝），否则会像这次一样把崩溃留到运行时才暴露。
