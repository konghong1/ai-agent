### 5. 严重后端 bug：保存提供商模型时视频/默认模型丢失（根因已定位并修复）
- 症状：预览拉取 chat/video/image 正确，保存后视频组消失、计数不对。
- 根因：`app/services.py` 中三处 `select(Model).where(...).update({...})` 是**非法 SQLAlchemy 2.0 写法**（Select 对象无 `.update()`）。
  - `create_model`（保存模型）在 `is_default_X=True` 时触发 → 抛 `AttributeError: 'Select' object has no attribute 'update'` → 500 → 前端判失败、该默认模型未落库。
  - 每种类型的第一个（默认）模型都会失败。视频常仅 1 个且为默认 → 整组消失；聊天/图片常有多模型，非默认者留下 → 看起来"只剩聊天和图片"，计数错。
  - 另外 `create_provider`/`update_provider` 在 `is_default=True` 时也有同样写法（新建时默认 false 故未触发）。
- 修复：统一改为 `from sqlalchemy import update as sa_update` + `sa_update(Model).where(...).values(...)`。三处全部修正。
- 验证：TestClient 端到端（造 token→建 provider→存 chat/video/image/embedding→调 /api/providers-chat）全部 200，返回 `chat:1 video:1 image:1`，video 正常、计数正确。已清理测试数据，real providers 完好。
- 提示：该 bug 会让"设为默认"的模型静默丢失，影响很大，建议团队 code review 时重点留意 SQLAlchemy bulk update 写法。

### 8. 媒体代理 `/api/media/proxy` 返回 401 + by-key 路由从未注册（已修复）
- 症状：前端 `<img>/<video>` 加载 `/api/media/proxy?url=<外部CDN>` 与 `/api/media/assets/by-key/...` 时返回 `401 Unauthorized`，图片/视频全部加载失败。
- 根因（两处独立）：
  1. **代理端点带鉴权**：`app/api.py` 的 `proxy_media` 有 `Depends(get_current_user)`，但浏览器加载媒体资源时**不会**附带 Bearer 头 → 必然 401。代理本身已有域名白名单（`_MEDIA_PROXY_ALLOWED_DOMAINS` = `platform-outputs.agnes-ai.space`）做 SSRF 防护。
  2. **by-key 路由是孤儿、且自身导入即崩**：
     - `app/server.py` 只 `include_router(router)`（app.api），**从未挂载 `media_routes.router`** → `/api/media/assets/by-key/...` 在生产里根本不存在。这意味着上一轮让视频走 by-key 的改动等于走到不存在的端点，视频只能回退到外部代理（→401）。
     - `app/media_routes.py` 顶部 `from app.storage import ... get_storage_backend` 但该函数**只存在于 `app.media_new`** → 模块导入即 `ImportError`，整份媒体路由无法加载。
     - 还有 `/assets/{asset_id}` 路由签名 `request: Request | None = None` 是非法 FastAPI 参数类型（注册时报 `FastAPIError`）。
- 修复：
  - `app/api.py` `proxy_media`：去掉 `current_user` 与鉴权（保留域名白名单 SSRF 防护）。媒体元素无法携带 token，公开代理是必要取舍，且域名受限。
  - `app/media_routes.py`：导入改为 `from app.media_new import get_storage_backend`；补 `Depends` 导入；删除 `/assets/{asset_id}` 的 `request: Request | None = None` 非法形参。
  - `app/server.py`：新增 `from app.media_routes import router as media_router` 并 `app.include_router(media_router)`。
  - 图片也落盘 MinIO：`app/api.py` `_handle_image_generation` 在拿到 `image_url` 后调用 `MediaService._download_and_store(image_url, "image")`，优先用 by-key 内部链接；失败则回退原 CDN（仍可经已修好的代理）。至此视频+图片同架构（生成→下载→存 ai-agent-minio→by-key 流出）。
  - `get_media_by_key` 加固：依据扩展名返回正确 `content-type`（原写死 `application/octet-stream`），并支持 HTTP `Range` 请求（视频可拖动，返回 206 + `Content-Range`）。
- 验证（TestClient 实测）：代理无 token → 白名单外 403 / 白名单内 502（非 401，鉴权已移除）；by-key 端点 → `200` + `video/mp4`、`Range` → `206` + `Content-Range`、`image/png` 正确。
- 经验：FastAPI 路由若导入即报错（如 ImportError / 非法参数类型），该 router 不会被注册，但其端点会被"静默缺失"。新增/修改 router 后务必确认 `include_router` 已挂载，并用启动期路由收集或一次冒烟测试验证。

## 根因：媒体（图片/视频）从未写入 ai-agent-minio 桶

### 现象
用户反馈：聊天框生成的图片/视频没有保存到 MinIO 的 `ai-agent-minio` 桶（之前一直在用外部 CDN 直链或本地 `./media`）。

### 真正的根因（两层）
1. **`get_storage_backend` 导入目标错误（致命）**：`app/api.py` 实际调用的是 `app/media.py` 的 `MediaService`（生成主路径）。`app/media.py` 里 `from app.storage import get_storage_backend` —— 但该函数**只定义在 `app/media_new.py`**，`app/storage/__init__.py` 里根本没有。于是每次 `_download_and_store` 走到 `get_storage_backend()` 都抛 `ImportError`，被外层 `except` 吞掉，回退到原始外部 CDN URL —— 文件从未进桶。之前只修了 `media_routes` 的导入，漏了生成主路径 `app/media`。
2. **`boto3` 未安装（次致命）**：`MinIOStorageBackend` 懒加载 boto3，`put()` 在没装时会 `ImportError`。`requirements.txt` 缺 `boto3`。即使上面修好，没 boto3 仍存不进去。
- 附带：默认 `STORAGE_BACKEND` 为 `local`；`docker-compose` 的 `minio-init` 建的是 `media-assets` 桶而非 `ai-agent-minio`；worker 默认桶也是 `media-assets`（三方命名混乱）。

### 修复
- 把 `get_storage_backend()` 真正落地到 `app/storage/__init__.py`（单一真相源，默认 `minio` + 桶 `ai-agent-minio`，修正 `MINIO_PUBLIC_URL` 默认桶名），`app/media.py`、`app/media_new.py`、`app/media_routes.py` 全部改从 `app.storage` 导入。
- `requirements.txt` 加 `boto3>=1.34.0`，并装到受管 venv（Docker 镜像经 requirements 自动带入）。
- `app/media.py._download_and_store` 重构对象键结构为 `images|videos/{user_id}/{yyyy}/{mm}/{dd}/{uuid}.{ext}`，返回后端代理路径 `/api/media/assets/by-key/{key}`（浏览器可达），MIME/扩展名推断更稳。
- 聊天流落库 `MediaAsset`：`_handle_image_generation` 与 `get_video_status` 端点生成/完成时写入（user_id、object_key、status=completed），便于管理与清理。
- `docker-compose`：`minio-init` 建并公开 `ai-agent-minio`；api/worker 的 `MINIO_BUCKET` 默认回退改为 `ai-agent-minio`；根 `.env` 显式补 `STORAGE_BACKEND=minio` + MINIO_*。worker 默认桶与 SQL(`NOW()`→`CURRENT_TIMESTAMP`) 同步修正。

### 验证
- 全部改动文件 `py_compile` 通过；`get_storage_backend()` 解析为 `MinIOStorageBackend`，桶 `ai-agent-minio`；`media_new.get_storage_backend is storage.get_storage_backend` 为 True（已统一）。
- 无法在本环境起 MinIO 实测上传，但导入链路与默认配置均已闭环。注意：已运行容器需 `pip install boto3` 或重建镜像方能生效。

### 问题3：聊天生成的视频「生成不出来」
- **核查结论**：完成→展示→入库整条链路代码正确（watch 下发 `status:completed,video_url`(by-key)，前端 `ChatInterface` `MediaCard.VideoCard` 内联 `<video>`；`get_video_status` 在 provider 返回 URL 时 `_download_and_store` 落 MinIO 并产出 `object_key`）。e18a/ad362 视频确实完成并被 serve。

- **本项目「漏 commit」是高频坑**：`get_db` 只 `yield db` 不自动提交，凡 `db.add/flush` 后必须显式 `db.commit()`（图片生成在 `_handle_image_generation` 有 commit 故正常，视频/模板路径缺 commit 才出事）。新增任何写库逻辑务必确认 commit。

## Bug 修复：聊天选本地参考图报 "Request Entity Too Large" (413)

### 现象
用户在聊天框选本地图片 + 配置后，前端直接返回 `413 Request Entity Too Large`，且看不到图片上传。

### 根因
- nginx vhost（`docker/nginx.conf` → 容器 `/etc/nginx/conf.d/default.conf`）**未设 `client_max_body_size`**，nginx 默认上限 **1MB**。
- 参考图以 **base64 data URL 内联在聊天请求体**里发送（设计如此，无单独上传步骤），一张本地图轻松超 1MB → nginx 在请求到达后端前就拒掉，返回 413。
- 「看不到上传」是设计预期：参考图不单独上传，而是随聊天请求体一并发出。413 阻断了发送，故用户以为没上传。

### 修复
1. **nginx**：`docker/nginx.conf` server 块加 `client_max_body_size 50m;`（bind-mount，改完 `nginx -s reload` 即生效，持久化）。
2. **前端健壮性**：`handleRefFiles` 改用 `downscaleImage(file)` —— 用 canvas 把所选图片最长边压到 1280px、重编码为 JPEG q0.85 再 base64。普通照片从数 MB 降到 ~100-200KB，从源头避免超限、也更快。
3. 空读保护：`Promise.all` 后 `filter(Boolean)` 去掉读取失败产生的空串，避免坏缩略图。

### 验证
- 前端 `tsc --noEmit` 0 错；`vite build` 通过（新 bundle `index-8COgjFB7.js`）；nginx reload 后线上引用新包。
- **413 实测**：经 nginx(80) POST 一个 ~5MB base64 请求体 → 返回 `401`（到达后端、鉴权拒），**不再 413**，证明 body 上限已放开。

## 本轮补完：GlassButton 类型债清零 + 「参考图生成页面内容消失」排查

### 1. GlassButton 类型债（用户要求一起修）
- 根因：`GlassButtonProps extends ButtonProps` 又重声明 `variant?: 'primary'|'secondary'|'ghost'|'danger'`，与 antd v5 `ButtonProps.variant`（仅 `'link'|'text'|'dashed'|'solid'|'outlined'|'filled'`）冲突 → `TS2430`。
- 修复：`extends Omit<ButtonProps, 'variant'>` 后重声明自定义 `variant`。`variant` 本就在组件内被解构消耗、不转发给 `<Button>`，故运行时零影响。

### 2. 「上传本地图片为参考图生成视频/图片」页面内容消失（排查）
- **关键事实**：该功能**不在独立页面**，而是集成在聊天页 `web/src/pages/ChatInterface/index.tsx` 的输入框工具栏（📎 参考图按钮 + 🎛 高级参数（图片尺寸 / 视频时长）），始终渲染、无模型类型门槛。它在源码与当前 `dist` bundle（`index-BJV5k893.js`，含 "参考图"×3）里都**真实存在**，并非被删除。
- **真正根因（部署缓存）**：`docker-compose.yml` 的 `web` 服务是裸 `nginx:alpine`，**bind-mount `../web/dist`**，里面没有任何 build 步骤——所以 `start.bat`（`compose down`+`up --build`）**不会重建前端**，`web/dist` 是什么就服务什么。而 `docker/nginx.conf` 此前**完全没有 `Cache-Control`**：

  - 验证：`curl -I` 确认 `/` 与 `/index.html` 返回 `no-cache`、`/assets/...js` 返回 `immutable`。
- **用户侧操作**：现在只需在浏览器**硬刷新一次**（Ctrl/Cmd+Shift+R）清掉旧的缓存 `index.html`，之后每次 `vite build`+`nginx reload`（或 `start.bat`）都会自动拿到新入口，不再 404。
