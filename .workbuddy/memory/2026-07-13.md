## 登录报 "Invalid email or password" 根因（同日晚续）
- **现象**: 修好白屏后，用户用 `kh1763751448@gmail.com` 在 `localhost:80` 登录报密码错，但自称密码对。
- **根因**: 两套独立用户库——Docker 栈 MySQL(`ai_agent`，localhost:80 登录走这) 与 本地 SQLite(`agent.db`，uvicorn:8010 走这)。同一邮箱 `kh1763751448@gmail.com` 在两库**密码哈希不一致**(DIFFER)，用户记得的是 SQLite 那套密码，但登录走 MySQL 那份哈希 → 校验失败。
- **修复**: 把 SQLite `agent.db` 该账号的 `password_hash` + 确保 `enabled=1` 同步进 MySQL(`UPDATE users SET password_hash='...' WHERE email=...`)。同步后两库哈希 MATCH，用户原密码即能在 localhost:80 登录。无需重启服务(校验是实时读库)。
- **排查套路**: 先 `docker exec ai-agent-mysql mysql ... "SELECT email FROM users"` 看账号在哪套库；再比对重名账号在两库的 `password_hash` 是否相等(pbkdf2 前缀相同要看完整串)；同步哈希即可。
- **修正(同日晚)**: 单纯"同步 SQLite 哈希到 MySQL"对用户 `kh1763751448@gmail.com` 仍 401——因为用户给的真实密码跟两套库的哈希都**对不上**(SQLite 那份也不是用该密码设的)。最终用 `app.core.security.hash_password(真实密码)` 生成哈希，直接 `UPDATE` 进 MySQL+SQLite(两库同步)，再实测 `POST /api/auth/login` 两栈均返回 200+token 才确认修好。**教训**: 用户说"密码对"但两边哈希都不匹配时，别只同步旧哈希，直接用用户提供的真实密码重设最稳妥。(记忆中勿存明文密码)
