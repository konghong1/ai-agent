## MemoryPanel「点击接受/拒绝页面没反应」收尾

- **根因（最终确认）**：`main.tsx` 用 `<AntApp>` 包裹整站。antd 在 React 19 + `<App>` 下，组件内必须用 `App.useApp()` 取 `message`/`modal` 实例；静态 `message.success()` 在 `load()`（多 setState）之后的异步路径下「不报错但 holder 从未创建」→ toast 不可见。Login 静态 message 能工作是因为在简单同步提交 handler。
- **修复**（`web/src/pages/MemoryPanel/index.tsx`）：改用 `const { message, modal } = App.useApp()`；`Modal.confirm`→`modal.confirm`；`load()` 无条件先于 toast 执行（列表刷新独立于 toast 可靠性）。`src/styles/global-theme.css` 保留 `.ant-message{top:8px!important}` 等兜底。
- **验证**：Playwright+Chromium 对 web:80 生产构建。列表 `待确认候选 (1)→(0)`、后端 pending 1→0、toast 进入动画后稳定在 `top:16`（视口内），截图 `verify-shots/accept_toast_48.png` 为证。
- **清理**：删除 14 个 debug 脚本 + 2 张 debug 截图 + 临时日志；保留 `playwright_accept_visible.cjs`（唯一回归脚本，依赖 `seed_pending.py` 在 api 容器内种 MySQL 候选）。
- **⚠️ 测试陷阱（再记一次）**：`seed_pending.py` 必须在 `docker exec -w /app ai-agent-api python seed_pending.py` 容器内运行（继承容器 MySQL `DATABASE_URL`）；在容器外直跑会连 SQLite，候选对 API 不可见，导致假 404。其输出是 `SEEDED_ID=N`（不是 `id=N`）。

## ADR-025: 用户长期记忆「跨会话召回」缺口诊断（Proposed，待落地）

- **用户真实诉求（澄清）**：ai-agent 平台自己的聊天能提取并存储用户偏好（落 `user_memories`），但**同一用户跨会话时模型拿不到这些偏好作参考**。与 ADR-024（项目级 `.workbuddy/memory/MEMORY.md` 注入）是两码事——ADR-024 不解决用户偏好召回。
- **根因（read path 缺口，已用代码追踪确认）**：`ContextService.build()` 的"长期记忆"注入只有三条路径，且都依赖当前轮文本或未启用设施：
  1. `_core_memory()` 仅加载 `layer==0`（身份）；用户偏好默认 `layer==1` → 永不加载。
  2. `_retrieval_reflex(current_text)` 先 `_extract_entities` 抽触发词（我喜欢/我的/记住/@），新会话首句无触发词 → 返回空 → 不注入。
  3. `_semantic_recall`（Chroma）唯一能脱离触发词的语义召回，但 `ENABLE_MEMORY_RECALL` 在生产被注释关闭（docker/.env 注明"未配 embedding 端点"），fail-open 返回空。
  → **没有"会话开始无条件加载该用户偏好"的基线路径。** 存得进库却召不回。
- **方案（两层级）**：Tier1 = 新增 `_user_profile_memory(user_id)` 无条件加载 `active`+`layer>=1` 偏好/事实（importance desc、token 上限、预算≤15%、fail-open、user_id 隔离），新开关 `enable_user_profile_memory`（默认关）；Tier2 = 配 embedding 后开语义回忆作补充。推荐先落地 Tier1（零新依赖、直接修失忆）。
- **实现要点已写入** `designs/ADR-025-cross-session-memory-recall.md`（含 settings/context_service/docker 三处改动与验证步骤）。
- **已落地并验证通过（2026-07-18 11:2x）**：Tier1 实现 + 验证全绿。
  - 改动：`settings.py`(+`enable_user_profile_memory`/`user_profile_max_tokens`=2000/`user_profile_count_cap`=30)、`context_service.py`(+`_user_profile_memory()` 查 `active`+`layer>=1`+`mem_type in(preference,fact,correction)` 按 importance 降序、token/条数上限截断、fail-open)+`build()` 注入点；`docker/.env`+`docker-compose.yml` api environment 启用 `ENABLE_USER_PROFILE_MEMORY=true`（compose 注入优先级>根.env，须两端补）。
  - 验证：容器内开关生效；`_user_profile_memory(1)` 返回 725 字符块含真实偏好；`build()` 以无触发词「帮我写一段 Python 代码」仍注入画像块；真实 `POST /api/chat` 新线程 thread-dd042028be77 首句无触发词，模型回「根据长期记忆设定，开场白是"你好，小花生"」精确命中独特偏好 `开场白要求=你好，小花生`，跨会话召回确认生效。
  - Tier2 语义回忆未做（生产无 embedding 端点）。admin 记忆库含早期 MemoryPanel 测试噪声行（`确定性验证键…`/`标记：Z…`），非本次引入，未删。
  - 本次验证新线程 thread-dd042028be77（admin，2026-07-18）留待用户决定是否清理（`delete_thread` 硬删须谨慎）。
- **关键区分**：ADR-024=项目级记忆；ADR-025=用户级偏好跨会话召回。两者独立，互不替代。

### Batch 5（23:00-23:15）— Skill 价值澄清 + 双登录权限方案
- **Skill 价值澄清（用户困惑解答）**：用户问"Web 配 Skill 有啥用、怎么对接聊天"。读 `skill_runtime.py`+`agent.py:504-528` 确认机制：① `get_skill_catalog()` 只把技能名+描述+触发词摘要塞系统提示 ② LLM 判断匹配后主动调 `use_skill(name)` 工具 ③ `load_skill_content()` 从 DB 取 content 全文塞回上下文 ④ LLM 按全文 SOP 生成。**核心澄清**：Web Skill ≠ 代码，是"带触发词的可复用提示词 SOP"；唯一不可被替代的能力是"团队共享 prompt 模板 + 触发自动化 + Hook 联动"，纯 prompt 也能做到，价值最虚。建议：代码留着降级为"团队共享提示词库"，不再投入；真给 AI 加能力走 MCP。
- **双登录权限方案**：用户要"管理员和用户分开两套登录"。读 `deps.py`+`api.py:156-195`+`Login/index.tsx` 摸现状：单 User 表+role 字符串+手写 admin 检查+单登录页。决策**方案 B 逻辑分流**（一套后端+双前端入口+依赖守卫），否决方案 A 物理双入口（拆服务=过度工程）。方案要点：User 加 `is_superuser`；`require_superuser`/`require_team_role()`/`can()` 三个守卫；权限三层 is_superuser(系统级)/TeamMembership.role(团队级)/PermissionOverride(功能级)；前端 `/login`→CLayout + `/admin/login`→AdminLayout + RequireSuperuser 守卫；JWT 只放 user_id 每次查 DB 保证实时。5 批迁移可回退。

## Batch 5 · 团队权限模型设计（ADR-027 Proposed）
- **触发**：用户确认走团队方向，要求设计可控的、到功能级的权限控制 + C端自注册 + 团队创建/加入/邀请流程。

## Batch 6 · ADR-028 落地：单登录 + is_superuser 权限驱动菜单（已落地并验证）

- **触发**：用户否决双登录方案（"管理员就该一次登录看到所有菜单，为啥登两次"），要求按"单登录 + 权限驱动菜单"实现一版。先出细化方案 `designs/plan-adro28-impl.md`（ADR-028），再落地。
- **核心决策（替代 ADR-027 团队空间，本版只做系统级超管）**：
  - 所有用户（含管理员）走同一 `/login`；登录后菜单按 `user.is_superuser` **叠加**渲染（非三选一），超管专属项：MCP Server / Skills / Hooks / 用户管理。
  - 两种管理员互不干涉：①系统管理员(`is_superuser`，靠 seed 或提拔产生) ②团队管理员(ADR-027 后续，本版不做)。
  - 超管配置：`.env` 读 `INIT_SUPERUSER_EMAIL`/`INIT_SUPERUSER_PASSWORD`；`require_superuser` 守卫集中替换散落的 `role != "admin"` 检查。
- **后端改动**：`User.is_superuser`(Boolean,默认0)；运行时 `_migrate_sqlite_columns` 加列(BOOLEAN 可带默认值，避开 MySQL 1101)；`schemas.py` UserRead/UserUpdate/UserManagementRead 加字段；`db/__init__.py` seed 创建 `is_superuser=True` admin；`deps.py` 新增 `require_superuser`；`services.py` 三处 `role` 检查改 `is_superuser`；`api.py` 新增 `POST /admin/users/{id}/promote`、`/demote`（防自降级+防降级最后一位）。
- **前端改动**：`auth.ts` User 加 `is_superuser/enabled`；`BasicLayout.tsx` 加 `filterMenuByRole(items, isSuper)`，超管专属 key 非超管移除；`UserManagement/index.tsx` 加超管守卫(`!is_superuser`→重定向 `/dashboard`)+超级管理员列+编辑开关。
- **验证（铁律，隔离环境未碰真实库）**：
  - 后端：种子库验证(产出超管 admin)+真实库副本验证(迁移加列、守卫 403 拦截、promote 200/demote-self 400/demote-other 200)，全绿。
  - 前端：Playwright 真实浏览器，隔离 uvicorn(8011)+vite(5173)双上下文(超管/普通)。13 断言全过：超管见 4 个管理项、普通用户 4 项全隐、普通用户直达 `/users` 重定向 `/dashboard`。
  - 验证后已停隔离 8011/5173 进程，真实 8010/80(Docker)保持运行；临时脚本/库/日志全部清理。
- **验证中发现并修复的预存缺陷（超出本 ADR 但阻塞核心功能）**：
  1. **`gallery_tasks.name` 缺失 → 新建套图任务崩溃**：运行时 `init_db()` 路径(`_migrate_sqlite_columns`)此前未补齐 `GalleryTask.name`，仅 CLI `sync_model_columns` 覆盖。修复：在 `_migrate_sqlite_columns` 追加可空 `name VARCHAR(200)` 迁移；隔离库回归新建 GalleryTask 成功。
  2. **历史库 `username=admin` 残留永不被提拔为超管**：真实 agent.db 有残留 `username=admin`(email=`admin@admin.com`、非超管)。原 seed 记录存在即跳过→重启后管理员永不为超管、菜单不可见。修复：`seed_database` 改为已存在且非超管时仅补 `is_superuser=True`（**不动 password/email**）；隔离副本验证残留被提拔、22 普通用户无一是误提。
