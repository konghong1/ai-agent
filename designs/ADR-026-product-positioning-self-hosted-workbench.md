# ADR-026: 产品定位收窄为「自托管小团队 AI 工作台」

## Status
Accepted

## Context

项目最初 PRD（2026-06-24）定位为「本地可部署的 AI Agent 管理平台」，目标用户同时包含 Admin / Developer / 普通用户三类。随着功能堆叠（Auth、KB、Chat、Memory、电商套图、MCP/Skill/Hook 扩展面），出现以下症状：

1. **定位漂移**：平台层（扩展底座）与产品层（垂直应用，如套图）界限模糊，功能没有明显主次。
2. **persona 错位**：MCP/Skill/Hook 配置是开发者概念，却以 Web 控制台形式呈现给所有用户，造成"网页配扩展不合适"的直觉。
3. **过度工程倾向**：为自托管场景规划"万级并发 HA"，与真实使用规模（小团队 ≤10 人）严重不匹配，负 ROI。
4. **竞争焦虑**："通用 AI 平台"定位会与 Dify / FastGPT / Coze 正面竞争，单人/小团队无法支撑。

根本问题不是技术选型（Web vs 桌面）错误，而是**叙事主线丢失**——把"扩展底座"当成了"用户功能"来推。

## Decision

将产品定位从「通用 AI Agent 管理平台」收窄为「**自托管小团队 AI 工作台**」。

具体含义：

1. **三层结构明确化**
   - **底座层**（Auth + Provider + Chat + KB + Memory）：基建，不再增加横向功能。
   - **扩展面层**（MCP + Skill + Hook）：给管理员/开发者用的扩展接口，**不作为产品卖点推给终端用户**；Web 配置页降级为"高级设置"。
   - **垂直应用层**（电商套图等）：真正的产品价值产出，是开发重点。

2. **技术栈维持 Web**（FastAPI + React + Docker），不转桌面（Tauri/Electron）。理由：
   - 现有服务端架构（MySQL/MinIO/ChromaDB/worker 线程）是服务端资产，转桌面等于自废武功。
   - 多用户/远程访问/套图后端重活在 Web 架构下天然成立。
   - 沉没成本最大、收益最小的转型路径。

3. **扩展面的 Web 配置保留，但重新归类**：作为管理员域功能存在，不进入终端用户主路径。MCP/Skill/Hook 的真正回报是"快速试新垂直应用"，而非"配置体验本身"。

4. **HA/并发降级**：「万级并发」标记为过早优化。metrics 端点保留作观测；多副本/队列解耦等在真实出现瓶颈前不投入。

5. **开发重心转移**：停止横向扩展底座；把电商套图做深做透；基于扩展面快速孵化新垂直应用验证想法。

## Consequences

**变容易的**：
- 功能优先级判断有了准绳：能产出垂直价值的优先，纯平台横向能力暂缓。
- "这个功能给谁用"不再纠结：底座给所有人、扩展面给管理员、垂直应用给终端用户。
- 不必追赶通用平台的特性广度，专注自己用得爽。
- MCP/Skill/Hook 的成功标准清晰化：能否在一天内孵化一个新垂直应用。

**变困难的**：
- 电商套图必须真正做深做透，不能停留在 demo——它是目前唯一的垂直产品，成败在此。
- 扩展面（MCP/Skill/Hook）的"易用性"投入可以降低，但"稳定性/安全"不能降——它支撑垂直应用。
- 若未来真要走向 SaaS/多租户，需要重新评估定位（届时本 ADR 被 superseded）。

**不变的**：
- 技术栈、现有代码、Docker 部署方式全部保留。
- 多用户/权限体系保留（自托管团队场景仍需要）。
