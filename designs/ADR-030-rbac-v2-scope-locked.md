# ADR-030: RBAC v2 范围锁定 — 动态菜单 + 全局角色 + 内容共享单列

## Status
Accepted（用户 2026-07-19 确认）

## Context
在 `plan-permission-rbac-v2-system-module.md`（Proposed）评审中，有三个开放点需要拍板，否则无法开工：

1. **菜单是否数据库驱动（动态菜单）** —— 用户此前已确认要"资源可新增 = 菜单自动出现"，故必须选动态菜单（资源表驱动），而非保留硬编码。
2. **角色是否按团队细分** —— 用户明确"团队不细化角色了"，即角色一律 **global**，多团队差异化授权继续走现有成员级 `user_permissions` override（两级委派不变）。
3. **"团队"的真实语义** —— 用户揭示核心诉求："创作案例发布可以给多个团队使用"。这把"团队"定义为**内容的分发/可见性单元（协作空间语义）**，而非数据的拥有者。对应前序讨论中的"解法②（出生归个人 + 显式共享）"：数据归创建者(`user_id`)，通过"发布/共享到团队"的关联表让多个团队可见/可用，**不引入 `team_id` 数据归属**，从而从根上回避"多团队下数据归谁"的悖论。

## Decision
- **动态菜单**：新增 `Resource` 表（`type='menu'` 带 `parent_code` 树）驱动侧边栏，替换 `BasicLayout` 硬编码 `menuItems`；保留静态快照作 fallback 防白屏。
- **全局角色**：新增 `Role` / `RolePermission` / `UserRole` 三张表，`user_roles.team_id` 首版恒 `NULL`（预留但不使用）；**不做团队级角色细分**。
- **团队 = 权限壳 + 内容分发单元**：保留 `team_admin_scopes` + `user_permissions` 两级委派作为 override 层；"创作案例发布给多团队"作为**独立后续 Phase 5（内容共享）**，不在本次权限改造内，但本次奠基的权限/团队体系为其服务。
- **判定逻辑**：`can()` 维持加性并集（角色权限 ∪ 个人 user_permissions ∪ 团队 scope），超管恒真；无负权限。

## Consequences
- **得到**：运营/超管可自助新增菜单与权限资源、无需发版；基础角色 `base` 等价于现状 `PERSONAL_DEFAULT`，自注册用户天然持最基础菜单；团队作为内容分发单元的语义被显式锁定，避免后续误做成"数据租户"（硬隔离）。
- **放弃 / 代价**：
  - 不做团队级角色模板 —— 若将来确实需要"每个团队自定义角色"，需给 `roles`/`user_roles` 加 `team_id` 并补管理 UI（模型已预留，可逆）。
  - 数据保持 `user_id` 归属，因此"团队 A 拥有专属数据"不可达 —— 这与用户诉求一致（用户要的是"发布给多团队用"，不是"团队独占数据"）。
  - 动态菜单使布局加载多一次接口（已用缓存 + 静态 fallback 缓解）。
- **预测性**：纯加性、无负权限，判定结果可枚举、可审计；`is_system` 保护内置角色/权限不被误删。
